# sleeve: the POWERarm app manager (terminal UI) -- design

Written 2026-09-19. **Implemented 2026-09-20/21**: `sleeve` has been fully implemented, verified
against all Phase 1 & 2 gates, and extracted into a standalone companion repository at
`~/Development/sleeve` (multi-backend: `POWERarm` for AArch64 and `fastppcx86` for x86_64).
Every `file:line` was checked against the tree at `e76bc2e4d`. Read `HANDOVER.md` ("What POWERarm is for",
item 8, 11, 17, 21, 24, 25) and `DESIGN.md` §6.2a first; this document builds on them and does not repeat them.

## 0. Summary

`sleeve` is a small C++ terminal program, built standalone (and deployable across both POWERarm and
fastppcx86), that turns "an emulated program somewhere on disk" into "an app that launches from the
Omarchy launcher and runs under the emulator with the right rootfs and options". It replaces the
hand-written launchers of 2026-09-19 (`~/.local/bin/{code,firefox,factorio}` and their
`*-arm64.desktop` entries) with generated, regenerable ones, and gives the owner a place to flip the
emulator's per-app knobs without editing JSON by hand. Standalone repo: `~/Development/sleeve`.

It does five things, each also available as a plain CLI subcommand so an agent or a script can drive
it without a terminal:

1. **Find** arm64 software: scans chosen directories for AArch64 executables, archives and bundles
   that contain them, and the apps guest `pacman` installed into a rootfs overlay. Groups them into
   apps by shape (Electron, Gecko, SDL/GL game, CLI, single-binary runtime, AppImage, .deb, pacman).
2. **Wrap**: writes a `~/.local/bin/<name>` launcher and a
   `~/.local/share/applications/<name>-arm64.desktop` entry with icon and `StartupWMClass`. Shows
   every file before writing; never overwrites a file it did not write.
3. **Configure** per app: rootfs, code cache and scope, compare-fusion kill switch, ProfileStats and
   MangoHud, portable/dev-emulator mode, and the app-shape presets. Emulator settings go to
   `~/.config/powerarm/AppConfig/<program>.json`; the settings the emulator cannot carry for a whole
   process tree (rootfs, toolkit variables, app arguments) go in the launcher. §5 says which is which
   and why.
4. **Rootfs**: finds what the environment already says, lists rootfses and overlays, points at an
   existing one, or sets one up through the existing scripts; detects an app's missing libraries
   with the guest `ld.so` and installs them with the sealed guest `pacman`; optionally persists the
   default in the user's shell rc, shown as a diff first.
5. **Health check**: runs the app briefly and says in plain words what the emulator reported.

**Decisions, in short.** C++20 in-tree with FTXUI as an `External/` submodule (system package first,
like fmt), one code path for TUI and CLI, one JSON record per app as the source of truth from which
launcher, desktop entry and AppConfig are regenerated idempotently, and Omarchy's terminal palette as
the default colour scheme with the current theme's exact accent read from `colors.toml`.

**Name.** `sleeve`, decided by the owner on 2026-09-19: it makes wrappers for arm binaries, and a
sleeve is what wraps an arm. The command is `sleeve`, the CMake target and package component are
`powerarm-sleeve`, the config directory is `~/.config/powerarm/sleeve/`. No package in the Arch or
ALARM repositories ships a `sleeve` binary. The name still lives in exactly one place,
`set(SLEEVE_NAME "sleeve")` in `Source/Tools/Sleeve/CMakeLists.txt`, passed as a compile definition,
and everything user-visible derives from it: the binary, the record directory, the marker line in
generated files (`# generated by sleeve`), the rc block markers and the `X-Sleeve-*` desktop keys.
Should it ever change again, that is one CMake line plus a `git mv` of the source directory, and the
ownership check keeps a list of previous names so files written under an old name are still
recognised as ours (§4.4).

## 1. Scope

In scope: everything in §0, for the user's own directories, with the emulator and rootfs tooling that
exist today. Out of scope, on purpose: registering binfmt (needs root; sleeve shows the command and
reads the registration state), promoting the stable build, building rootfses for other
distributions, editing `Config.json` beyond its `RootFS` key, and anything that runs an app's code
for detection (detection is by bytes; running is the explicit health check).

Non-goals that were considered and dropped: a GTK/Qt GUI (FEXConfig exists and is not what the owner
asked for; a TUI works over ssh to the POWER9), a daemon or tray (nothing needs to be long-lived),
and a plugin system for app shapes (a table in one file is enough for the five shapes that matter).

## 2. Facts from the code that shape the design

These are the load-bearing observations. Each later section cites them rather than restating them.

**F1. Config layers and their order.** `FEX::Config::LoadConfig` (`Source/Common/Config.cpp:478-519`)
adds, in order: the global `Config.json`, the user `Config.json`, the global and local per-app
layers, `FEX_APP_CONFIG` (an explicit file, `:505-515`), then the environment (`:517`). The meta
layer applies them in `LoadOrder` (`FEXCore/Source/Interface/Config/Config.cpp:117-122`): later
wins, so **environment beats AppConfig beats Config.json**. The environment loader reads every
`POWERARM_<OPTION>` variable (`Source/Common/Config.cpp:281-338`; prefix at `:289`, option walk at
`:330-337`).

**F2. The per-app config is keyed by the program's basename.** `GetApplicationNames`
(`Source/Common/Config.cpp:430-476`) sets `ProgramName` to the filename of `argv[0]` (`:443`), and
`GetApplicationConfig` (`FEXCore/Source/Interface/Config/Config.cpp:93-111`) maps that to
`<config dir>/AppConfig/<ProgramName>.json`. The file format is the same as `Config.json`: a
`"Config"` object of `"Name": "value"` strings (`Source/Common/Config.cpp:32-83`; unknown names are
logged and ignored, `:231`). So VS Code's config is `AppConfig/code.json`, Firefox's
`AppConfig/firefox.json`, Factorio's `AppConfig/factorio.json`, and each applies to **every** guest
process with that basename, including an app's own helper children (`code --type=zygote`,
`firefox -contentproc`).

**F3. A guest child process starts from scratch.** `execve` of a guest program goes back through
binfmt (or through the same emulator in portable mode, F5). The only things the parent emulator
injects into the child's environment are `POWERARM_EXECVEFD`, `POWERARM_SECCOMPFD` and
`POWERARM_EXECVEARGV0` (`Source/Tools/LinuxEmulation/LinuxSyscalls/Syscalls.cpp:654-669, 768`).
Nothing forwards the parent's RootFS or any other option. The child re-reads F1's layers with **its
own** basename. What it does inherit is the guest environment, which the loader passes verbatim
(`Source/Tools/FEXInterpreter/ELFCodeLoader.h:594-602`) plus the `Env` option's entries
(`:604-607`, from `FEXInterpreter.cpp:613`). Hence `POWERARM_ROOTFS` exported by a launcher reaches
`sh`, `git`, `xdg-open` and every other child; an AppConfig `RootFS` reaches only processes named
like the app. This is why tonight's launchers export the rootfs, and why they are right to.

**F4. AdditionalArguments are appended to every launch of that name.**
`ELFCodeLoader.h:575-576` appends the `AdditionalArguments` list to the guest argv. With F2 that
means `--profile DIR` in `AppConfig/firefox.json` would also be appended to `firefox -contentproc
...`. App arguments therefore belong in the launcher, not in AppConfig.

**F5. Portable mode.** `POWERARM_PORTABLE=1` (read as `FEX_PORTABLE` through the env-prefix wrapper,
`Source/Tools/CommonTools/PortabilityInfo.h:19-38`, `Source/POWERarm/EnvPrefix.cpp`) makes the
emulator ignore binfmt and run children through itself (`FEXInterpreter.cpp:350-354`), skips the
global layers (`Config.cpp:482-489`), and moves the data directory next to the binary
(`Config.cpp:619-621`), which is why a rootfs given **by name** resolves to nothing under it
(HANDOVER trap, lines 123-126). The local AppConfig layer is still loaded (`Config.cpp:491`). sleeve
therefore always writes rootfs paths as absolute paths, never names.

**F6. Rootfs lookup by name.** `ReloadMetaLayer` (`FEXCore/Source/Interface/Config/Config.cpp:352-368`)
tries `<dir>/RootFS/<name>` for the global then local data and config directories, last match wins.
The user data directory is `$XDG_DATA_HOME/powerarm/` or `~/.local/share/powerarm/`
(`Source/Common/Config.cpp:616-647`; a legacy `~/.powerarm/` takes precedence if it exists,
`:629-634`). The overlay is `<rootfs>-overlay` when that directory exists, or the `RootFSOverlay`
setting (DESIGN §6.2a.1 "Activation"). sleeve mirrors this order exactly (§8.1).

**F7. What the emulator says when things go wrong, and where.**
- `Unimplemented A64 instruction 0x%08x at pc 0x%x` is an Info-level log
  (`FEXCore/Source/Interface/Core/A64Frontend/IRBuilder.cpp:437`), emitted at translation, not
  execution (HANDOVER lines 145-146); only a SIGILL exit (132) proves execution.
- `POWERarm: FATAL host fault: signal N (si_code C, addr 0x..) at host nip 0x..` goes straight to
  stderr (`Source/Tools/LinuxEmulation/LinuxSyscalls/SignalDelegator.cpp:1712, 1728`).
- `POWERarm: '<path>' is not a supported ELF: ...` goes to stderr
  (`Source/Tools/FEXInterpreter/FEXInterpreter.cpp:681`), also when a named rootfs failed to
  resolve and a host binary was found instead (F5).
- Logs are silent by default (`SilentLog` true, `OutputLog` `server`); `POWERARM_SILENTLOG=0
  POWERARM_OUTPUTLOG=stderr` routes every level to the process's stderr
  (`FEXInterpreter.cpp:141-155, 209-232`). `stderr` is the right sink for a check because children
  inherit it; a file would be `O_TRUNC`ed by every child (`:240-244`).
- A missing library is glibc's own `error while loading shared libraries: X: cannot open shared
  object file`, and `<rootfs>/usr/lib/ld-linux-aarch64.so.1 --list <exe>` prints `X => not found`
  without running the program.

**F8. The existing ELF parsers.** `ELFParser::ReadElf` (`Source/Tools/CommonTools/Linux/Utils/ELFParser.h:21-140`)
validates magic, class, endianness, `e_machine == EM_AARCH64` (`:96-99`), `e_type` (`:101-104`),
reads the program headers and `PT_INTERP` (`:126-134`), and offers `VAToFile` (`:157-168`) and a
`PT_DYNAMIC` walk pattern (`HasCodeRelocations`, `:185-193`). It logs every rejection through
`LogMan::Msg::EFmt`, so a scanner must pre-filter with its own 64-byte probe before calling it.
`ELFContainer::GetDynamicLibs` (`Source/Tools/CommonTools/Linux/Utils/ELFContainer.cpp:567-605`)
reads `DT_NEEDED` but only after slurping the whole file into `RawFile` (221 MB for the Claude
binary), so sleeve reads `DT_NEEDED` itself through `ELFParser`'s headers (§6, `ElfInspect`).

**F9. The existing tooling sleeve drives, never reimplements.** `build-alarm-sysroot.sh`
(`Scripts/powerarm/rootfs/build-alarm-sysroot.sh:1-22` for its flags) builds a pinned base;
`alarm_sysroot.py overlay-init --dest <overlay> --base <base> --with-pacman [--manifest M]
[--package P]` bootstraps guest pacman into an overlay and refuses to register a base twice
(`Scripts/powerarm/rootfs/alarm_sysroot.py:891-925`, the refusal at `:897-898`); the pacman dance
is `POWERARM_PORTABLE=1 POWERARM_ROOTFS=<base> unshare -r POWERarm /usr/bin/pacman ...`
(`Scripts/powerarm/rootfs/README.md:273-280`), sealed by default (DESIGN §6.2a.1 "Sealed view");
MangoHud is built into the vk overlay by `Scripts/powerarm/mangohud/build-mangohud.sh` and used with
`MANGOHUD=1 LD_PRELOAD='/usr/$LIB/mangohud/libMangoHud_shim.so' MANGOHUD_CONFIG=...,fex_stats
POWERARM_PROFILESTATS=1` (`build-mangohud.sh:22-24`); the stats live in
`/dev/shm/powerarm-<pid>-stats` (`Scripts/powerarm/shmstats.py:5-6`).
`promote-powerarm-stable.sh` copies a build's `Bin/` and `Data/` to `~/.local/opt/powerarm-stable`,
so anything sleeve needs at run time from the tree must be under `Data/` in the build directory.

**F10. Omarchy's current theme.** `omarchy-theme-set` stages the theme into
`~/.local/state/omarchy/current/next-theme`, renders the templates, then swaps the directory into
`~/.local/state/omarchy/current/theme` and writes the snake-case name to
`~/.local/state/omarchy/current/theme.name` (`/usr/share/omarchy/bin/omarchy-theme-set:284-296`).
`colors.toml` lives in that directory; its keys vary by theme (cobalt2 has `accent`, `cursor`,
`selection_foreground`, `selection_background`; the current `drac` has `accent`, `selection` and no
cursor key), and the one resolver every Omarchy consumer uses is `omarchy-theme-color
[--file F] --all`, which prints sorted `key<TAB>value` pairs after the alias cascade
(`selection_background` <- `selection` <- `color8` <- `color0` <- `background`;
`selection_foreground` <- `bright_foreground` <- `color15` <- `foreground`; `cursor` =
`bright_foreground`; `muted` <- `color8`; `mode` dark/light from the background's luminance;
`/usr/share/omarchy/bin/omarchy-theme-color:176-291`). Templates `~/.config/omarchy/themed/*.tpl`
(user) and `$OMARCHY_PATH/default/themed/*.tpl` (built in) are rendered at theme-set time into
`current/theme/<name-without-.tpl>`, a file the theme itself ships wins, and placeholders are
`{{ accent }}`, `{{ accent_strip }}`, `{{ accent_rgb }}` and `{{ mix a b 30% }}`
(`omarchy-theme-set-templates:375-397`). Running terminals are retinted with OSC 4/10/11/12/17/19
(`omarchy-theme-osc`, `omarchy-theme-set-foot`) or restarted (`omarchy-restart-terminal`). foot,
alacritty and ghostty all include the rendered file from `current/theme/`
(`~/.config/foot/foot.ini:2`, `~/.config/alacritty/alacritty.toml:1`, `~/.config/ghostty/config:2`).

## 3. Screens and flows

One `ftxui::ScreenInteractive::Fullscreen()` with a two-pane main screen and modal overlays for
previews and questions. Keys are shown on the bottom line of every screen. Every action that writes
opens the preview modal first (§3.7); nothing writes from a list screen directly. All mockups are
100 columns.

Colour roles in this mock, cobalt2 values in brackets (`~/.config/omarchy/themes/cobalt2/colors.toml`):
- `sleeve ·` in the title and the `▶` marker: **accent** (`#ffc600`, truecolor from `colors.toml`;
  falls back to Palette16 yellow).
- The selected row `code ...`: **selection** (`#ffffff` on `#0050A4`, truecolor; falls back to
  `inverted`).
- `✓`: Palette16 green (`color2`, `#3ad900`); `?` and `foreign launcher`: Palette16 bright black
  (`color8`, `#0050A4`, the theme's "muted"); an error would be Palette16 red (`color1`, `#ff628c`).
- Everything else: the terminal's default foreground on its default background (`#ffffff` on
  `#122738`). sleeve never paints a background of its own outside the selection row, so terminal
  transparency and blur are untouched.
- Box borders and the key line: default foreground, borders `borderRounded` in muted.

Note on cobalt2 specifically: its `color8` equals its `selection_background`, so muted text on the
selected row would vanish. The selected row therefore renders every cell in `selection_foreground`;
status glyphs keep their meaning through the glyph, not the colour.

The status line reads the stable version from `~/.local/opt/powerarm-stable/VERSION`, the binfmt
entry from `/proc/sys/fs/binfmt_misc/POWERarm-aarch64`, and "inode verified" only after
`Scripts/powerarm/check-binfmt-inode.sh` has passed this session (it runs on demand from `[r]`,
never automatically, because it starts a guest process).

`[n]` runs `build-alarm-sysroot.sh --dest <RootFS>/<name> --manifest <choice>` in a log pane

builds and a64diff bundles are keyed to the bare base. `[d]` edits only the `RootFS` key of
`Config.json` (§4.5).

## 4. Data model

### 4.1 Locations

| What | Path | Owner |
|---|---|---|
| App records | `~/.config/powerarm/sleeve/apps/<name>.json` | sleeve |
| Settings | `~/.config/powerarm/sleeve/settings.json` (scan dirs, prune list, apps dir, last theme) | sleeve |
| Rootfs notes | `~/.config/powerarm/sleeve/rootfs/<name>.json` (which manifest built it, when) | sleeve |
| Emulator per-app config | `~/.config/powerarm/AppConfig/<program>.json` (F2) | shared: sleeve writes the keys it manages, keeps the rest |
| Emulator user config | `~/.config/powerarm/Config.json` | the emulator's; sleeve edits only `Config.RootFS` on request |
| Launcher | `~/.local/bin/<name>` | generated |
| Desktop entry | `~/.local/share/applications/<name>-arm64.desktop` | generated |
| Unpacked apps | `<apps dir>/<name>-arm64/<version>/` + `current` symlink; apps dir defaults to `~/Development` if it exists, else `~/.local/opt` | the user's |
| Scratch | `$XDG_CACHE_HOME/powerarm/sleeve/` (health logs, files-db index) | sleeve |

All paths derive from `FEX::Config::GetConfigDirectory/GetDataDirectory/GetCacheDirectory`
(`Source/Common/Config.cpp:616-710`) so `XDG_*` and the legacy `~/.powerarm` are honoured the way
the emulator honours them.

### 4.2 The app record

One JSON file per app, the single source of truth; launcher, desktop entry and AppConfig are pure
functions of it and are regenerated from it.

              "origin": "/home/jbettcher/Downloads/code-stable-arm64.tar.gz" },

               "icon": "current/resources/app/resources/linux/code.png",

`source.kind` is `dir` (unpacked or found tree), `file` (a lone executable such as Claude's
`versions/2.1.278`), or `pacman` (`{"kind":"pacman","rootfs":"…/ArchLinuxARM-vk","package":"firefox"}`,
with `exe` absolute inside the overlay). Relative `exe`/`icon` are relative to `source.dir`, so
switching `current` moves everything at once. `emulator` is `null` (stable through binfmt) or an
absolute path to a `POWERarm` binary (dev mode, §5). `appconfig` holds only emulator option names
that exist in `ConfigValues.inl` (validated at load; §6 `AppConfigWriter`); values are the strings
the emulator's JSON loader expects (`"1"`/`"0"` for booleans, as `FEXConfig` writes them,
`Source/Tools/FEXConfig/Main.cpp:116`).

### 4.3 Generated artefacts

**Launcher** (`~/.local/bin/<name>`), POSIX `sh`:

```sh
#!/bin/sh
# generated by sleeve  record=~/.config/powerarm/sleeve/apps/code.json  -- edit the record, not this
# Visual Studio Code (arm64) under POWERarm. Regenerate with: sleeve wrap code
export POWERARM_ROOTFS="${POWERARM_ROOTFS:-$HOME/.local/share/powerarm/RootFS/ArchLinuxARM-vk}"
export ELECTRON_OZONE_PLATFORM_HINT="${ELECTRON_OZONE_PLATFORM_HINT:-auto}"
exec "$HOME/Development/vscode-arm64/current/bin/code" --no-sandbox "$@"
```

Variants: `cd "<dir>" && exec ./bin/arm64/factorio "$@"` when `cwd` is `install`; the dev-mode
form is `export POWERARM_PORTABLE=1` (unconditional, because a named rootfs would break, F5) plus
`exec "<emulator>" "<exe>" ...`; MangoHud adds the three exports from F9 and
`POWERARM_PROFILESTATS=1`. `${VAR:-default}` keeps the launcher overridable from a terminal, which
is how tonight's files behave.

**Desktop entry** (`~/.local/share/applications/<name>-arm64.desktop`):

```ini
[Desktop Entry]
Type=Application
Name=Visual Studio Code (arm64)
Comment=Visual Studio Code under POWERarm
Exec=/home/jbettcher/.local/bin/code %F
Icon=/home/jbettcher/Development/vscode-arm64/current/resources/app/resources/linux/code.png

StartupWMClass=Code
X-Sleeve-Managed=true
X-Sleeve-Record=/home/jbettcher/.config/powerarm/sleeve/apps/code.json
```

`Icon` is an absolute path (Omarchy's launcher and Hyprland resolve it; the three existing entries
do the same). After writing, `update-desktop-database ~/.local/share/applications` runs if present
(`mimeinfo.cache` exists there, so it is in use).

**AppConfig** (`~/.config/powerarm/AppConfig/code.json`):

```json
{
  "Config": {
    "RootFS": "/home/jbettcher/.local/share/powerarm/RootFS/ArchLinuxARM-vk",
    "EnableCodeCachingWIP": "1",
    "CodeCacheScope": "home",
    "DisableCmpBranchFusion": "0",
    "ProfileStats": "0"
  }
}
```

`RootFS` is written here too, as an absolute path, so running the ELF by hand (`POWERarm
~/Development/vscode-arm64/current/code`, or under gdb) gets the right rootfs; the launcher's
export still wins for the whole tree (F1, F3). Both come from the record's one `rootfs` field, so
they cannot disagree.

### 4.4 Ownership and idempotency

Every write goes through one `FileWriter` (§6) that decides per path:

| On disk | Marker | sha256 == record | Verdict |
|---|---|---|---|
| absent | - | - | **new**: write |
| present | sleeve (any known name) | equal | **managed**: replace silently in the preview list |
| present | sleeve | differs | **hand-edited**: show the diff, ask |
| present | none | - | **foreign**: never overwrite; offer another name or an explicit move-aside |

Markers: the `# generated by sleeve` line for shell files, `X-Sleeve-Managed=true` for desktop
entries, and for AppConfig the record's list of keys it manages: sleeve rewrites those keys and
preserves every other key and every other top-level object (`AppOverrides`, `ThunksDB`), because
`SaveLayerToJSON` would drop them (`Source/Common/Config.cpp:91-138` writes only `Config` and
`ThunksDB`, from a 4 KiB buffer, `:115`). Writes are atomic (temp file in the same directory,
`rename`), and the record stores the sha256 of what was written. Regenerating with no change
produces a byte-identical file, so a repeated `sleeve wrap` is a no-op and the preview says so.

A rename of the tool keeps `SLEEVE_LEGACY_NAMES` in the same CMake file; markers written under any
listed name count as ours.

### 4.5 Config.json edits

Only the `Config.RootFS` key, only from §3.4 `[d]`, only by a targeted rewrite of the parsed
`json_t` tree (tiny-json, as `LoadJSonConfig` walks it, `Source/Common/Config.cpp:46-83`) that
re-emits every other key and object unchanged, and shown as a diff first. By name (as README
line 78 shows) unless the user has `POWERARM_PORTABLE` in their rc, in which case by absolute path
with a note (F5).

## 7. Omarchy theme integration

**Default: the terminal's 16-colour palette.** Every colour role maps to an FTXUI `Color::Palette16`
index, which the terminal renders from its own palette. Omarchy themes that palette in foot, alacritty
and ghostty through the rendered `current/theme/<terminal file>` (F10) and retints running foot
windows with OSC 4 on a theme switch, so a running sleeve follows a theme change with no work of its
own beyond a redraw, and outside Omarchy it looks like any other TUI in whatever palette the user
has. Roles:

| Role | Palette16 | Truecolor override (Omarchy only) |
|---|---|---|
| accent (title, selection marker, active tab, `[keys]`) | Yellow (3) | `accent` |
| selection row | `inverted` | `selection_foreground` on `selection_background` |
| ok / warn / error / info | Green (2) / Yellow (3) / Red (1) / Blue (4) | none (the palette is already themed) |
| muted (secondary text, borders, "foreign") | GrayDark (8) | none |
| text / background | default / default (never painted) | none |

**On Omarchy: exact accent and selection.** At start, on `[t]`, and when the theme changes, sleeve
resolves the palette in this order and shows the source in the status line:

1. `--theme FILE` or `$SLEEVE_THEME` (a `colors.toml`; for tests and screenshots).
2. `~/.local/state/omarchy/current/theme/colors.toml` (F10), resolved by running
   `omarchy-theme-color --file <it> --all` when that command is on `PATH`, because it is the one
   resolver every Omarchy consumer shares and it handles the key variations (drac has no
   `selection_background`, only `selection`). Its output is `key<TAB>value`, sorted, hex values.
3. If the command is missing but the file exists: sleeve's own 40-line reader for
   `key = "#rrggbb"` lines with the same six fallbacks (`accent` <- `color3`; `selection_background`
   <- `selection` <- `color8` <- `color0` <- `background`; `selection_foreground` <-
   `bright_foreground` <- `color15` <- `foreground`), copied from
   `omarchy-theme-color:225-231`.
4. Otherwise Palette16 only ("theme: terminal palette").

Truecolor is used only for the two roles in the table; FTXUI degrades an `RGB` colour to the nearest
palette entry by itself when `Terminal::ColorSupport()` says the terminal has no truecolor, so the
code has one path. The theme name in the status line is `theme.name` (`omarchy-theme-current`
reads the same file).

**Re-reading.** `omarchy-theme-set` replaces the `theme` directory by `rm -rf` + `mv` of
`next-theme` and then writes `theme.name` (F10), so sleeve watches the parent
`~/.local/state/omarchy/current/` with inotify (`IN_MOVED_TO | IN_CREATE | IN_CLOSE_WRITE`) from a
small thread that posts a custom event through `ScreenInteractive::Post`, exactly the shape
`FEXConfig` uses for its RootFS directory (`Source/Tools/FEXConfig/Main.cpp:272-292, 344-360`). The
handler re-resolves (step 2 or 3) and redraws. `[t]` does the same by hand, for the case where
inotify is unavailable.

**Template or direct read?** Direct read, for these reasons: a `themed/sleeve.toml.tpl` renders only
at theme-set time and only if it sits in the user's `~/.config/omarchy/themed/` (a package cannot
install there; `$OMARCHY_PATH/default/themed/` is Omarchy's own), so sleeve would have to write into
the user's config on first run, would still need the direct read as a fallback until the next theme
switch, and would get nothing the direct read does not already give, since the templates are
rendered from the very same `omarchy-theme-color --all` output (`omarchy-theme-set-templates:381`).
What a template is good for is user customisation of the roles, so sleeve **honours one if it
exists**: if `current/theme/sleeve.toml` is present (the user created
`~/.config/omarchy/themed/sleeve.toml.tpl`), its `accent`, `selection_background`,
`selection_foreground`, `ok`, `warn`, `error`, `info` and `muted` keys override the table above,
and `sleeve theme --print-template` prints a sample template to paste there. No file is ever
written into `~/.config/omarchy/` by sleeve.

## 8. Rootfs discovery, setup and missing libraries

### 8.1 Discovery (same order as the emulator, F6)

1. `POWERARM_ROOTFS` in sleeve's own environment (absolute, or a name resolved as in 3).
2. `Config.RootFS` in `~/.config/powerarm/Config.json`, then `/usr/share/powerarm/Config.json`.
3. Every directory, `.sqsh` and `.ero` under `~/.local/share/powerarm/RootFS/` and
   `/usr/share/powerarm/RootFS/` (`DATA_DIRECTORY`, `CMakeLists.txt:61`), plus the config-dir
   variants the meta layer also tries (`FEXCore/.../Config.cpp:363`). A name ending in `-overlay`
   is attached to its base, not listed on its own.

Per rootfs sleeve shows: base size, overlay presence and size, whether `var/lib/pacman/local` in the
overlay holds packages (guest pacman bootstrapped), package count, which records use it, and, from
`~/.config/powerarm/sleeve/rootfs/<name>.json` or the `<cache>/<name>.contents` listing the build
script leaves (`build-alarm-sysroot.sh:47-49`), which manifest built it. Images cannot have a
directory overlay unless `RootFSOverlay` names one (DESIGN §6.2a.1), and the row says so.

### 8.2 Setup through the existing tooling

All three are subprocess plans shown before they run, streamed into the log pane, with the exact
command line visible and copyable:

- **New base:** `build-alarm-sysroot.sh --dest <RootFS>/<name> --manifest <m2|vk|path>`; on success
  sleeve writes its rootfs note (manifest, date, content hash from the script's output).
- **Overlay + guest pacman:** `mkdir <base>-overlay`, `alarm_sysroot.py overlay-init --dest
  <base>-overlay --base <base> --manifest <the one that built the base> --with-pacman`, then, with
  `POWERARM_PORTABLE=1 POWERARM_ROOTFS=<base>` (the README's exact recipe,
  `Scripts/powerarm/rootfs/README.md:273-280`), `unshare -r <emulator> /usr/bin/pacman-key --init`,
  `--populate archlinuxarm`, `pacman -Sy`. The emulator is the stable one unless the record says
  otherwise. sleeve refuses to add an overlay to a rootfs whose note says "M2 gate" without a
  second confirmation (the README's warning).
- **Host fonts (item 17):** `ln -s /usr/share/fonts ~/.local/share/powerarm/host-fonts` and the
  `60-powerarm-host-fonts.conf` snippet into `<overlay>/etc/fonts/conf.d/`, both shown first.

`POWERarmRootFSFetcher build` now runs exactly that sequence (base, overlay, the three pacman
steps, the config write) and `POWERarmRootFSFetcher overlay <base>` runs the second half on an
existing base, so sleeve can shell out to one command instead of three (DESIGN §6.2a.0). When
`Scripts/powerarm/rootfs/setup-desktop.sh` exists (item 17), sleeve calls it for the whole
sequence instead; until then it runs the steps itself. The scripts are found through `Paths` (build
tree `Data/rootfs/`, copied there by CMake so `promote-powerarm-stable.sh` carries them, F9; or
`/usr/share/powerarm/rootfs/` when installed).

### 8.3 Missing libraries

`sleeve libs NAME` runs `<emulator> <rootfs>/usr/lib/ld-linux-aarch64.so.1 --list <exe>` with the
record's environment (rootfs, `LD_LIBRARY_PATH` if the launcher sets one), parses `X => not found`,
and maps each soname to an Arch Linux ARM package. The host's `pacman -F` cannot do that (its
databases are ArchPOWER's ppc64le ones), and the overlay's sync directory holds only `core.db`,
`extra.db`, `alarm.db` (no `.files`). So the map comes from the repo files databases:
`<mirror>/<repo>/<repo>.files` for `core`, `extra`, `alarm`, downloaded into
`~/.cache/powerarm/alarm-pkgs/` next to the `.db` files `alarm_sysroot.py` already caches
(`alarm_sysroot.py:193-194, 805-808`), by a new `alarm_sysroot.py whatprovides [--repos ...]
usr/lib/libgtk-3.so.0 ...` subcommand that prints `path<TAB>package<TAB>repo<TAB>version` (Python
`tarfile` reads the `.files` tarballs; the mirror and cache flags already exist). sleeve shells out
to it; no archive parsing in C++. A refreshed index is offered when it is older than a day. The
alternative, guest `pacman -Fy` + `pacman -F`, works too and is offered as "use pacman's files
database instead" (it needs the sealed uid-0 dance and a 100+ MB download into the overlay).

Installation is the sealed guest pacman: `unshare -r <emulator> /usr/bin/pacman -S --needed <pkgs>`
with the README environment, which writes only into the overlay (DESIGN §6.2a.1 "Verified
2026-09-18"). The plan lists the packages, then runs, then re-runs `ld.so --list` to confirm.

### 8.4 Unpacking

| Kind | Detection | Unpack |
|---|---|---|
| `.tar.gz`/`.tar.xz`/`.tar.zst` | `bsdtar -tf` listing; arm64 by file-name hint (`arm64`, `aarch64`) or by extracting the first executable-looking member to the cache and probing it | `bsdtar -xf FILE -C <dir>/<ver>` with `--strip-components=1` when the listing has exactly one top-level directory |
| AppImage | ELF + `AI\x02` at offset 8 | squashfs offset = `e_shoff + e_shnum * e_shentsize`; `unsquashfs -o OFFSET -d <dir>/<ver> FILE` (squashfs-tools >= 4.5); fallback `<emulator> FILE --appimage-extract` |
| `.deb` | `ar` magic; `control` has `Architecture: arm64` | `bsdtar -xOf FILE 'data.tar.*' \| bsdtar -x -C <dir>/<ver>` |

Version: from the archive name (`\d+(\.\d+)+`), else `product.json`/`package.json`/`application.ini`
inside, else the date. Never into an existing version directory (§3.6).

## 9. Health check

Runs the launcher (so the real environment and arguments apply) as a child with pipes, adds
`POWERARM_SILENTLOG=0 POWERARM_OUTPUTLOG=stderr` (F7), `--version` for shapes that have it (electron,
gecko, runtime, cli; Factorio also honours it), otherwise runs for `--seconds` (default 20) and sends
`SIGTERM`, then `SIGKILL` after 5 more. Default cap 120 s because the first run after a promote is
cold (HANDOVER line 56). When `HYPRLAND_INSTANCE_SIGNATURE` is set and `hyprctl` is on `PATH`, the
timed mode also polls `hyprctl -j clients` for a window whose `class` matches the record's WMClass
(the check HANDOVER item 21 did by hand).

Classifier, in the order lines are matched:

| Pattern (F7) | Plain words |
|---|---|
| `POWERarm: '...' is not a supported ELF` | "This is not an AArch64 program, or the rootfs did not resolve and a host binary was found instead. If the launcher uses a build path, the rootfs must be an absolute path." |
| `POWERarm: FATAL host fault: signal N ...` | "The emulator itself crashed (signal N at host address ...). This is an emulator bug; keep this line for the report." |
| `error while loading shared libraries: X` | "The program needs the library X and the rootfs does not have it." -> offers §8.3 |
| `Unimplemented A64 instruction 0xW at pc 0xP` (counted, deduplicated by W) | "The translator met N instruction(s) it does not implement (words ...). Only a SIGILL exit means one was executed; feature probes are expected (MRS TPIDR2/GCS, MTE, SVE, SME, HANDOVER lines 51-53)." |
| exit 132 / 139 / 134 | "Died with SIGILL / SIGSEGV / SIGABRT" plus the unimplemented words if any were logged |
| `Couldn't connect to POWERarmServer socket` | "The emulator server could not start; with a user namespace or a build path, set POWERARM_PORTABLE=1 (README line 274-275)." |
| timed out with a window seen | "Started and showed a window (class X); stopped after N s." |
| timed out, no window | "Ran for N s without a window; not necessarily wrong for a CLI program." |
| exit 0 | "Ran and exited normally" plus the first stdout line |

The raw output is kept at `~/.cache/powerarm/sleeve/health/<name>-<timestamp>.log` and the summary
goes into the record's `health` object.

## 10. Shell rc editor

Shell: basename of `$SHELL`, else the passwd entry (`FindUserHomeThroughUID`'s parser at
`Source/Common/Config.cpp:522-571` shows the field layout; sleeve reads the seventh field the same
way). File: bash -> `~/.bashrc` (with `~/.bash_profile` sourcing it, as here); zsh -> `~/.zshrc`;
fish -> `~/.config/fish/conf.d/sleeve.fish` (fish's drop-in directory, so no existing file is
edited at all). The block is delimited by `# >>> sleeve (POWERarm) >>>` / `# <<< sleeve (POWERarm) <<<`
(fish: same text, `set -gx` syntax); apply = replace the block if present, append if absent, no-op
if identical; remove = delete the block only. The diff is shown first (§3.8) with the Config.json
trade-off note, and the result is written atomically with the original's mode kept. Nothing else in
the file is touched, including the owner's fastppcx86 block.

## 12. Safety rules

1. **Never write into a rootfs base.** The only writes near a rootfs are the guest pacman's, which
   run sealed and land in the overlay (DESIGN §6.2a.1), and the fontconfig snippet, which goes into
   the overlay's `etc/`. sleeve refuses a rootfs path as a destination for anything else.
2. **Never write outside the user's own directories without asking**: `~/.local/bin`,
   `~/.local/share/applications`, `~/.config/powerarm/`, the apps dir, `~/.cache/powerarm/sleeve/`,
   the shell rc, and the overlay through pacman. `/opt` is scanned, never written. No `sudo`, ever;
   binfmt registration is shown as a command.
3. **Show every file before writing** (§3.7), including the ones the CLI writes under `--yes`
   when `--dry-run` is given; and every subprocess command line before it runs.
4. **Never overwrite a foreign file** (§4.4). Move-aside is explicit and keeps the original.
5. **Never run an app to classify it.** Detection is by bytes and file names; the health check is a
   named action.
6. **Never delete.** The only removals are the rc block (on request) and retargeting a `current`
   symlink; version directories stay.
7. **Never edit `Config.json` beyond `RootFS`**, and only through the targeted rewrite that keeps
   `AppOverrides` and `ThunksDB` (§4.5).
8. **Downloads only through the existing scripts**, which verify sha256 and signatures
   (`Scripts/powerarm/rootfs/README.md:27-37`).
9. **Portable + named rootfs is refused at generation time** (F5): a launcher with a build-path
   emulator always carries an absolute `POWERARM_ROOTFS`.
